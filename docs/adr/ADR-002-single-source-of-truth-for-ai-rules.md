# ADR-002: Single source of truth for AI rule files

## Context

Different AI coding assistants read their rules from different files:

- **Claude Code** reads `CLAUDE.md` in the project root.
- **OpenAI Codex / GitHub Copilot** reads `AGENTS.md`.
- **Gemini CLI** reads `GEMINI.md`.
- **Cursor** reads `.cursorrules` (legacy format) and `.cursor/rules/beacon.mdc` (modern format).

A naive approach would have developers maintain each file independently. This creates immediate
drift: one file gets updated, the others don't. Within a week the convention described to Claude
differs from the convention described to Cursor, defeating the entire purpose of having a shared
convention.

An alternative would be to auto-generate all files from the project config (`beacon.config.json`)
using pure logic — no human-authored source of truth at all. But this prevents project teams from
adding custom instructions to their AI agents (e.g., "for this project, always check the
integrations README before writing any Stripe code"). Pure generation from config alone produces
identical boilerplate for all projects, which is insufficient for real customization.

(Spec §5.1, §7.0)

## Decision

Establish `docs/_meta/convention.md` as the **single human-edited source of truth**. Running
`beacon sync` reads this file and regenerates all vendor AI rule files. Generated files carry a
header warning against direct edits:

```
<!-- generated by beacon — do not edit. Edit docs/_meta/convention.md and run `beacon sync`. -->
```

`beacon lint` (via the `ai-files-sync` rule) validates that each enabled vendor's file matches
what `beacon sync` would produce. If `convention.md` is edited without re-running sync, lint fails
with exit code 1.

The generated files are composed of two layers (see ADR-005):
- **Universal layer**: 9 rules identical across all projects.
- **Project-specific layer**: dynamically generated from the enabled category list in
  `beacon.config.json`.

Teams who need per-project custom instructions edit `convention.md` — they do not touch the
generated files. The linter enforces this invariant in CI.

## Consequences

**Positive:**
- All AI agents always see the same convention. No drift between vendors.
- `beacon sync` is idempotent and safe in pre-commit hooks.
- Project teams have a single place to customize agent behavior.
- The linter's `ai-files-sync` rule makes convention drift a CI failure, not a manual concern.

**Negative / Trade-offs:**
- Generated files cannot be hand-edited; contributors must learn the source-of-truth pattern.
  Mitigated by the `<!-- generated by beacon -->` header and lint errors.
- `beacon sync` must be run after every change to `convention.md`. Mitigated by lint enforcement
  and the recommendation to add `beacon sync` to a pre-commit hook.
- Adding support for a new AI vendor requires both a new generator module and registration in the
  `ai-files-sync` lint rule (see the "Adding an AI vendor" reference pattern).
